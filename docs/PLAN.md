# План разработки ESPBS

Обновлено 14 октября 2026 года. После каждого завершённого шага: относящиеся к нему тесты, обновление документации, коммит и push. Новый компьютер начинает с получения актуального `main` с сохранением имеющихся локальных правок.

Основной сценарий: парсер собирает на Selectel → пользователь скачивает партию ZIP/XML → проверяет архив → отдельно подтверждает освобождение места → сбор продолжается. Компьютер не обязан быть включён постоянно. Будущая загрузка в EnergoStore/OpenCart — отдельная задача.

## Этапы и критерии

| Этап | Результат | Как принимаем | Статус |
| --- | --- | --- | --- |
| 1. Хранение и архив | Отдельная SQLite-БД партии, порционное сохранение, XML/ZIP, независимая проверка | Повтор записи и экспорта, сбои процесса и упаковки, повреждённый архив | Ядро реализовано и проверено локально; CI добавлен |
| 2. Первый источник | Реальный адаптер одного производителя, серверная команда запуска, события и checkpoint | Небольшой реальный сбор, сверка карточек, остановка и продолжение; HTTP-фикстуры в обычных тестах | Реализован Eltex; локальный реальный сбор и остановка/продолжение проверены |
| 3. Управление и интерфейс | API, список заданий, прогресс, ошибки, серверный каталог и журнал в выбранном стиле | UI показывает реальные события и восстанавливает состояние после разрыва связи | Запланировано |
| 4. Полный цикл архивов | Вложения, ручное скачивание/докачка, подтверждение, очистка партии, квоты | Неполная копия не разрешает очистку; диск реально освобождается; сбор приостанавливается заранее | Запланировано |
| 5. Качество и дополнительные источники | Нормализация, причины QA, кандидаты в дубли, несколько адаптеров | Проверенные правила и примеры реальных данных; нет ложных автоматических объединений | Запланировано |
| 6. Desktop и Selectel | Сборка Windows, профиль подключения, запуск серверного процесса, расписание, инструкция | Проверка EXE на Windows и реального сервера; длительный запуск в пределах дискового лимита | Запланировано |

При разработке этапа 2 ограничивать реальные запуски числом товаров. До этапа 4 автоматической защиты диска и очистки ещё нет; оставлять неограниченный сбор на Selectel нельзя.

## Что есть после этапа 1

- `espbs/storage.py`: запись каждого принятого объекта в транзакции, идентичность по источнику и его ID/URL, обновление или пропуск повтора внутри партии.
- `espbs/archive.py`: фиксация партии, потоковое построение XML, ZIP с манифестом, контрольные суммы и проверка без исходной БД.
- `python -m espbs`: создание партии, импорт JSONL, список, статус, экспорт и проверка скачанного архива.
- Тесты сохранности и обработки ошибок без сетевых обращений.
- CI для Python 3.12 на Linux и Windows. GitHub Pages получает только файлы страницы.

### Проверки

Локально на Windows, Python 3.13.6: `python -m unittest discover -s tests -v` — 17 тестов прошли. В первом прогоне обнаружена ошибка `fsync` на дескрипторе, открытом только для чтения; режим открытия исправлен, полный набор повторён успешно.

Тесты используют явно синтетические записи, включая домен `example.invalid`. Это проверка ядра хранения, а не доказательство работы производителя или сервера Selectel.

### Ограничения этапа

- Подключён адаптер Eltex (см. COLLECTION.md). API и новый GUI пока не подключены. Старая `app.py` остаётся неполной и не запускается без отсутствующих адаптеров.
- XML содержит все переданные JSON-поля, в том числе ссылки на документы и изображения. Сами файлы не скачиваются и не упаковываются; в манифесте указано `references-only`.
- XML — собственный версионированный формат ESPBS, не готовый формат OpenCart.
- Очистки исходных данных нет. `ARCHIVED` означает «архив создан и проверен на этой машине», а не «пользователь скачал его домой».
- Межпартийная дедупликация, общий индекс источников и миграции следующих версий ещё не реализованы. Модель пока хранит последнее состояние исходной записи внутри партии, не полный канонический каталог.
- Экспорт требует места под сжатый архив рядом с БД. Квоты и автоматическая ротация партий появятся на этапе 4. XML ограничен 8 GiB, строка JSONL — 4 MiB.
- Запечатанная партия не принимает новые записи даже после ошибки упаковки. Её можно повторно экспортировать; новые результаты относятся к новой партии.
- Готовый ZIP публикуется через атомарную жёсткую ссылку в той же папке, без перезаписи существующего архива. Требуется файловая система с поддержкой hard links (например, NTFS или ext4). После аварийного завершения может остаться `.partial`; исходная БД сохраняется.
- Серверный доступ по SSH пока не получен. Развёртывание и сборку EXE не проводили.

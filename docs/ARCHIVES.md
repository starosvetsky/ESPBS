# Партии и XML-архивы: ядро этапа 1

Python 3.12+. Ядро использует стандартную библиотеку, не требует Tkinter, сторонних пакетов или подключения к сайтам. Команды выполняются из корня репозитория. Рабочие данные игнорируются Git.

## Команды

```shell
python -m espbs --data-dir data new
python -m espbs --data-dir data list
python -m espbs --data-dir data status BATCH_ID
python -m espbs --data-dir data ingest BATCH_ID input.jsonl
python -m espbs --data-dir data export BATCH_ID --output exports
python -m espbs verify exports/BATCH_ID.zip
```

Заменить `BATCH_ID` идентификатором из результата `new`. Команды выводят JSON, при ошибке возвращают ненулевой код. `verify` можно запускать на компьютере со скачанным архивом без серверной БД.

`ingest` — способ подключить существующий источник или проверить сохранение его выгрузки. Это не парсер сайта. Вход — JSONL: один JSON-объект на строку. Обязательные поля: непустые строки `source`, `source_url`, `name`. `external_id` при наличии должен быть строкой; если отсутствует или пуст, идентификатором становится URL. Прочие JSON-поля сохраняются. Каждая строка фиксируется отдельно; при ошибке строки ранее принятые данные остаются в партии. Можно повторно импортировать исправленный файл: одинаковые записи внутри партии пропускаются, изменившиеся обновляются.

Проверка обязательных полей обеспечивает минимальную структуру хранения. Она не заменяет QA по бренду, MPN, характеристикам и происхождению данных.

## Содержимое архива

- `products.xml`: XML UTF-8 с корнем `products`, версией и идентификатором партии. Каждый `product` содержит ID исходной записи, время сбора, хеш исходного JSON и поля.
- `manifest.json`: формат `espbs-batch`, версия 1, ID партии, время создания, количество записей, размер и SHA-256 XML, признак `attachments: references-only`.

Поля записываются как `field` с атрибутами `name` и `type`. Поддерживаются `string`, `number`, `boolean`, `null`, `object`, `array`. Вложенные объекты сохраняют ключи, массивы — порядок элементов. Такой формат не теряет неизвестные характеристики и вложенные данные из исходного JSON. Соответствие конкретному импортёру магазина будет отдельным преобразованием.

Записи читаются из SQLite по одной и сразу записываются в сжатый ZIP; промежуточная полная XML-копия на диске не создаётся. При этом на сервере одновременно остаются БД и готовый ZIP. Зафиксированные записи не удаляются.

## Состояния

`OPEN` → принимает записи.

`SEALED` → состав зафиксирован для экспорта. При ошибке упаковки состояние сохраняется, повторный экспорт разрешён.

`ARCHIVED` → ZIP записан и проверен, его контрольная сумма сохранена в БД. Это не подтверждение скачивания пользователем и не разрешение удаления.

Повторный экспорт в ту же папку проверяет существующий архив и соответствие содержимому партии. Повреждённый или чужой файл не перезаписывается. Экспорт в другую папку позволяет создать новую проверенную копию из сохранившихся записей.

## Проверка и ограничения

Проверяются состав ZIP, CRC при чтении, структура XML, идентификатор партии, количество записей, размер и SHA-256 XML. Результат включает SHA-256 всего архива. DTD и сущности запрещены, данные не извлекаются по путям из ZIP. Контрольные суммы выявляют повреждение; авторство архива они не подтверждают.

Текущая проверка не доказывает полноту каталога производителя или достоверность характеристик. Файлы документов и изображений на этом этапе не загружаются. Реальное скачивание, проверка локальной копии приложением и отдельное подтверждение очистки будут реализованы далее.

# Потоковые части: экспериментальный режим

В слое хранения добавлен opt-in журнал `record_changes`. Метод
`Batch.enable_change_log()` можно вызвать только для пустой открытой партии.
Повторный вызов безопасен. Обычный сбор его не включает; в API и панели
режим выбирается явно для нового задания. CLI collect пока без флага;
существующие базы автоматически не мигрируют.

## Связь со сборщиком — этап 3

Внутренний Python-интерфейс `Job.create(..., streaming=True)` включает новый
режим только для новой исходной коллекции. API и панель предоставляют флаг
с этапа 4. Режим по умолчанию выключен; существующие задания
не меняются. Автоматическое последующее обогащение вместе с ним отклоняется.

Перед запросом страницы/товара сборщик восстанавливает незавершённую часть,
формирует части при накоплении 25 версий и проверяет окно. Две неочищенные
части переводят задание в WAITING_PARTS без следующего запроса к источнику.
После независимой проверки архива и явной очистки части требуется ручной
resume. Скачивание и confirm-copy не освобождают окно. В конце сбора остаток
меньше 25 версий также формирует часть. Завершённое задание может иметь части,
которые ещё не скачаны. Автоматической упаковки ZIP/вложений этот шаг не добавляет.

Проверка окна и обработка карточки используют общую stream-gate блокировку
с созданием частей. Параллельная операция получает занятость, а не меняет окно
между проверкой и HTTP. До Batch.add подготовленный JSON фиксируется в
`item_commits` задания. После сбоя повтор берёт именно его без обращения к
изменившемуся сайту, восстанавливает каталог и отметку обработанного URL.
Удаление этой временной записи выполняется одной транзакцией с отметкой URL;
сама карточка и её версия остаются в партии. При отказе записи по бюджету
временная карточка сохраняется для диагностики/повтора, но бюджет не сбрасывается.
Одновременно нужен дополнительный объём под одну подготовленную карточку;
перед её сохранением также проверяется свободное место.

Лимиты журнала фиксируются в конфигурации задания: 10 000 версий и 64 МиБ
UTF-8 JSON payload суммарно. Счётчики обновляются атомарно вместе с записью
карточки и версии. Неизменный повтор не расходует бюджет, в том числе после
сбоя между записью карточки и отметкой обработанного URL. Превышение даёт
PAUSED_JOURNAL, новая версия и карточка не записываются. Лимит payload не равен
размеру SQLite: индексы, WAL и копии тоже занимают место; require_space остаётся.

Предел журнала проверяется при сохранении, после получения/разбора карточки.
Журнал остаётся у родителя даже после очистки частей, поэтому её выполнение
не снимает PAUSED_JOURNAL. Повтор resume не сбрасывает лимиты. Это ограниченная
партия, не бесконечная очередь: для дальнейшего сбора нужна отдельная партия
либо будущий согласованный механизм очистки истории. Оставшиеся версии можно
разделить через stream_parts.create_next; автоматического удаления нет.

После включения `Batch.add()` сохраняет текущую карточку и неизменную версию
в одной SQLite-транзакции. У версии есть последовательный `seq`, исходные
record_id, payload, SHA-256 и время сохранения. Повтор неизменной карточки
не добавляет версию; изменение и возврат к прежнему содержимому добавляют.
`Batch.changes(after, limit)` читает до 100 версий после числового курсора.
Пустая страница означает только отсутствие новых версий сейчас, не конец сбора.

Это закрывает проблему хеш-курсора: новая карточка с меньшим record_id не
пропадёт за уже пройденной границей. Ошибка записи журнала откатывает и
изменение карточки. После обрыва задание может повторить сохранение: если
содержимое не изменилось, второй версии не появится.

Цена — дополнительная копия payload для каждой изменившейся версии.
Журнал пока не очищается. Очистка партии с непустым журналом блокируется:
обычный ZIP содержит только текущие карточки и не подтверждает сохранность
всех предыдущих версий. Не включать журнал для длительного реального сбора
до реализации выгрузки и ограничения роста диска.

## Неизменные части

`espbs.stream_parts.create_next(parent, after=0)` создаёт готовую дочернюю
партию из журнала. Родитель остаётся открытым; блокировка сборщика не требуется.
Граница — до 25 версий и обычно до 40 ссылок на вложения. Одна большая карточка
остаётся целой. Встреча повторного record_id завершает часть перед следующей
версией: версия не теряется и попадёт в следующую часть.

Диапазон `(after, through]`, ID дочерней партии и отпечаток содержимого
сохраняются до копирования. Повтор курсора возвращает ту же часть; после сбоя
она восстанавливается из зафиксированного диапазона, а не из текущих карточек.
Все исходные поля, ID, payload, хеши и время сохраняются без изменений.
Диапазон доступен в `child.info()['stream_range']`. Следующий вызов принимает
его `through`. `None` означает, что новых версий пока нет, а не конец сбора.

Не более двух неочищенных частей. Новая допускается после обычного цикла
экспорта дочерней партии, независимой проверки, подтверждения и явной очистки.
Ни скачивание, ни подтверждение сами по себе окно не освобождают. Родительский
журнал не удаляется. Очистка дочерней части до завершения её публикации запрещена.

Потоковые части экспортируются в формат v3: манифест содержит
`source_batch_id` и `stream_range` с границами `(after, through]`. Корень XML
повторяет исходный ID и границы; каждая запись несёт `journal_seq`. Проверка
без БД требует ровно по одной версии на каждый номер диапазона и уникальные
record_id внутри части. Обновления одной карточки попадают в разные части.
Поддерживаются архивы ссылок и режим с вложениями. Обычные партии сохраняют v1/v2.

Перед экспортом исходная БД и регистрация части ещё должны быть доступны:
экспорт сверяет снимок с зафиксированным отпечатком и журналом родителя.
Незавершённая публикация, пропуски версий или расхождение снимка блокируют экспорт.
Готовый ZIP проверяется автономно; контрольные суммы не удостоверяют авторство
и не доказывают полноту каталога. Отчёт подтверждения копии сохраняет исходный
ID и диапазон. Очистка родительского журнала по-прежнему запрещена.

Ранее созданный ZIP v1/v2 потоковой части не перезаписывается: новый экспорт
откажет из-за несовпадения XML. Можно экспортировать в другую папку; такой
экспорт сам по себе не заменяет серверный архив или подтверждение копии.
При использовании opt-in сборщика окно приостанавливает и сбор. Самостоятельные
вызовы stream_parts.create_next лишь ограничивают создание частей.

Регистрация теперь выполняется до создания дочерних файлов: родитель сохраняет
ID, диапазон, количество и отпечаток одной транзакцией вместе с зависимостью.
После сбоя повтор использует этот ID, даже если ни одного дочернего файла ещё
нет. Каждая схема создаётся транзакционно в файле `.pending`, закрывается
и только затем получает имя `.sqlite3`. Индекс истории не видит неполных схем.
Оставшийся `.pending` восстанавливается на следующей попытке; никаких удалений
или поиска по похожим именам нет. Готовые существующие базы проверяются;
несовпадающая конфигурация вызывает ошибку без перезаписи данных.

Прежние зарегистрированные незавершённые части совместимы с восстановлением.
Незарегистрированные файлы, если они уже возникли в старой реализации, не
присваиваются автоматически: у них нет надёжной связи с родительским диапазоном.
Проверяется аварийный выход процесса; испытание физического отказа диска
или отключения питания не проводилось.

## Панель и API — этап 4

Проверка 24 октября: общий набор — 175 тестов, 185 секунд, успешно.
После последней защиты ручного вызова блокировкой задания отдельно прошли
17 API-тестов. Два Node-теста проверяют навигацию, устаревшие ответы,
переключение заданий и доступность кнопок при паузах; добавлены в CI.
В браузере на временных синтетических данных проверены отображение окна,
переход к части, подготовка ZIP и возврат к родителю с сохранённой паузой.
Цикл скачивания, проверки, подтверждения и очистки проверен через loopback API.
Независимое повторное ревью всего этапа 4 не проводилось: субагент завершился
по лимиту использования; перед серверной приёмкой это остаётся отдельной проверкой.

В форме нового задания есть выключенный по умолчанию переключатель
«Части во время сбора». API принимает `POST /api/jobs` с `streaming: true`.
Без явного auto_enrich последующее обогащение отключено; сочетание двух
включённых режимов отклоняется, существующие задания не меняются.

Карточка исходного задания показывает `stream`: бюджет журнала, занятость
окна, курсор и возможность подготовить остаток. Список читается отдельно:
`GET /api/jobs/{id}/stream-parts?after=0&limit=10`. Курсор — номер части,
не номер версии; размер страницы 1–100, панель использует 10. Список показывает
диапазон версий, готовность снимка и состояние подтверждения/очистки.
Незавершённая регистрация видна даже до создания дочерних файлов.

`POST /api/jobs/{id}/stream-part` принимает целочисленный `after` — курсор
версий из `stream.next_after`. Повтор достраивает ту же часть; отсутствие новых
версий возвращает `caught_up: true`, а не обещание завершения сбора. Ручной
запрос берёт блокировку задания: работающий сборщик не прерывается из-за гонки.
Обычные archive-part, archive-queue-start, архив родителя и обогащение родителя
через API для этого режима запрещены. Для ZIP открывается конкретная часть.

Панель объясняет WAITING_PARTS, PAUSED_DISK и PAUSED_JOURNAL. После явной
очистки освобождается место в окне и доступно ручное продолжение. При пределе
журнала кнопка продолжения недоступна: очистка частей бюджет не сбрасывает.
Подготовка, скачивание, независимая проверка, confirm-copy и cleanup используют
существующие операции дочерней партии; автоматического удаления нет.
